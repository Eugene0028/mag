# SecureTransfer — лабораторная работа 1 и РГЗ

DH в полной группе, DH в подгруппе простого порядка и MQV: локальный обмен,
обмен по TCP и замеры основных вычислений в процессорных циклах.

Общий код расположен в `securetransfer.common`, сценарии первой лабораторной —
в `securetransfer.lab1`. В `securetransfer.rgz` находятся потоковые шифры,
получение ключа из секрета MQV, передача файлов и сравнение вычислительных этапов.

## Требования

- **JDK 17** — компиляция и запуск Java-кода.
- **IntelliJ IDEA** — открытие проекта и запуск готовых конфигураций.
- **JNA 5.17.0** — уже находится в `lib/jna-5.17.0.jar` и подключена в модуле.
- **Bouncy Castle 1.86 и eSTREAMJ 2.0.0** — находятся в `lib/` и подключены
  к модулю вместе с исходниками для шифров РГЗ.

Арифметика больших чисел реализована через стандартный `BigInteger`.
JNA вызывает системные функции счётчиков процессорных циклов.
Её лицензия находится в `lib/JNA-LICENSE.txt`.
SHA3-256 предоставляется стандартным `MessageDigest` Java 17 и не требует новой библиотеки.

Выбор реализаций HC-128, Rabbit, Salsa20 и Sosemanuk, версии зависимостей,
лицензии и особенности API описаны в [lib/README.md](lib/README.md).

### Разделение кода и настроек

Все три пакета находятся в одном модуле IDEA. Общие классы доступны через обычные
импорты, переходы к объявлениям и Find Usages. Направление зависимостей:
`lab1 → common ← rgz`. Общий код получает настройки от вызывающего приложения.
В `common` размещаются компоненты, общие для лабораторной и РГЗ. Интерфейс
потоковых шифров и их реализации относятся к РГЗ и находятся в `rgz.cipher`.

`KeyAgreementProtocolFactory` создаётся с `GroupGenerationSettings` и
`ApplicationDataPaths`. Размеры групп и каталог данных передаются в её конструктор.
`BenchmarkSettings` содержит только прогрев, число серий и размер серии, поэтому
средства измерения можно использовать для любых вычислительных этапов.

| Сценарий | Класс настроек | p / q подгруппы | Каталог данных |
| --- | --- | --- | --- |
| Демонстрации первой лабораторной | `lab1/config/Lab1Settings` | 16 / 8 бит | `data/lab1/` |
| Измерения первой лабораторной | `lab1/config/Lab1Settings` | 1024 / 160 бит | `data/lab1/` |
| Подготовленные настройки приложения РГЗ | `rgz/config/RgzSettings` | 3072 / 256 бит | `data/rgz/` |

Каталоги создаются при записи соответствующих файлов. Существовавшие параметры
и результаты первой лабораторной перенесены из `data/params/` и `data/reports/`
в `data/lab1/`. Параметры, пары ключей и доверенные материалы приложений разделены.
При чтении проверяется соответствие размеров параметров настройкам; несовместимый
существующий файл вызывает ошибку. Клиент также проверяет размеры полученной группы.

## Потоковые шифры РГЗ — пункт 7

Общий интерфейс `rgz/cipher/StreamCipher` задаёт работу с HC-128, Rabbit,
Salsa20 и Sosemanuk. Все четыре реализации находятся в пакете РГЗ.

| Метод | Назначение |
| --- | --- |
| `getName()` | Название алгоритма для вывода и измерений |
| `getKeyLengthBytes()` | Требуемая длина ключа в байтах |
| `getInitializationVectorLengthBytes()` | Требуемая длина IV в байтах |
| `initialize(secretKey, initializationVector)` | Полная подготовка ключа и IV, начало потока |
| `processBytes(inputBytes, inputOffset, byteCount, outputBytes, outputOffset)` | Обработка очередной порции данных |

Использование готовой реализации HC-128:

```java
StreamCipher cipher = new Hc128Cipher();
cipher.initialize(secretKey, initializationVector);
cipher.processBytes(inputBytes, 0, byteCount, outputBytes, 0);
```

Повторные вызовы `processBytes` продолжают тот же поток. Порции могут иметь любую
длину; их границы не меняют результат. Для расшифрования создаётся отдельный объект
с теми же ключом и IV. Повторная инициализация начинает поток заново; новое сообщение
при том же ключе получает новый IV.

`StreamCipherAlgorithm` перечисляет четыре алгоритма. Вызов `createCipher()`
создаёт новый объект выбранной реализации. Rabbit и Sosemanuk дополнительно
реализуют `KeyAndIvSetupCipher`: `setupKey` выполняет подготовку ключа,
`setupInitializationVector` устанавливает IV, используя сохранённое состояние ключа.

### HC-128 — пункт 8

Класс `rgz/cipher/Hc128Cipher` использует `HC128Engine` из Bouncy Castle.
Он принимает ключ и IV по 16 байт, проверяет границы буферов и запрещает
обработку до инициализации. Данные можно заменять результатом в том же участке
массива; пересечение участков при разных смещениях запрещено.

Каждый вызов `initialize` полностью подготавливает новое состояние шифра.
Последующие вызовы `processBytes` продолжают его, в том числе при длине порции,
не кратной внутреннему размеру слова. При расшифровании используется тот же метод
с отдельным объектом, инициализированным теми же ключом и IV.

### Rabbit, Salsa20 и Sosemanuk — пункты 9–11

| Класс | Реализация | Ключ | IV |
| --- | --- | --- | --- |
| `RabbitCipher` | Собственный Java-код по RFC 4503 | 16 байт | 8 байт |
| `Salsa20Cipher` | Bouncy Castle, 20 раундов | 16 байт | 8 байт |
| `SosemanukCipher` | eSTREAMJ с сохранением остатка потока | 16 байт | 16 байт |

Rabbit хранит восемь слов состояния, восемь счётчиков и бит переноса. После
подготовки ключа сохраняется исходное состояние для установки каждого нового IV.
Представление ключа, IV и выходных слов — little endian; при сопоставлении
с целыми числами из приложений RFC учитывается порядок байтов.

Sosemanuk обрабатывает полные блоки по 80 байт через библиотеку, а остаток
сохраняет в адаптере. Следующий вызов использует этот остаток перед генерацией
нового блока. Границы порций не сдвигают ключевой поток.

### Сравнение четырёх шифров — пункт 12

В IDEA выберите **SecureTransfer - RGZ CipherBenchmarkMain** или запустите
`securetransfer.rgz.CipherBenchmarkMain`. Аргументы не нужны. В `RgzSettings` задаются:

| Настройка | Значение |
| --- | --- |
| `CIPHER_BENCHMARK_SETTINGS` | 2000 прогревочных операций; 100 серий по 10 операций |
| `KEY_STREAM_BLOCK_LENGTH_BYTES` | 65536 байт, то есть 64 КиБ |

Для всех четырёх шифров измеряются два общих этапа:

1. **Полная инициализация:** создание объекта, подготовка ключа и IV.
2. **Генерация потока:** обработка заранее выделенного нулевого буфера и запись
   результата в готовый выходной массив. Состояние продолжается между порциями;
   подготовка ключа и IV выполняется до замеров этого этапа.

Для Rabbit и Sosemanuk дополнительно измеряются **подготовка ключа** и **установка IV**
отдельными вызовами. У HC-128 и Salsa20 выбранный API подготавливает ключ и IV совместно,
поэтому раздельные значения для них не публикуются. Всего получается 12 этапов
и отдельная служебная серия пустой операции. Однократная загрузка классов JVM
происходит при подготовке и прогреве.

Генерация случайных входов, выделение буферов потока, работа с файлами и вывод
не входят в измеренные интервалы. Создание объектов входит в полную инициализацию.
Служебные затраты показываются отдельно и не вычитаются. Циклы нормируются на
операцию, а для потока — дополнительно на байт. Это учебное сравнение конкретных
Java-реализаций на текущем компьютере с учётом JIT, сборки мусора и адаптеров.

Результаты каждого запуска сохраняются отдельно:

```text
data/rgz/reports/stream-ciphers/<дата-время-идентификатор>/
├── measurements.csv  # Целые циклы каждой серии
└── report.html       # Таблица, условия, вывод и встроенная копия CSV
```

HTML строится из сохранённого CSV. Показатели первой лабораторной находятся

производительности не выполняет.

## Получение ключа шифрования — пункты 13–15

Классы `rgz/key/Sha3Hasher` и `rgz/key/MqvKeyDerivation` задают учебную схему РГЗ:

```text
S — общий секрет MQV
L = ceil(bitLength(p) / 8)
secretBytes = беззнаковое представление S старшим байтом вперёд, длиной L байт
hash = SHA3-256(secretBytes)                 # 32 байта
encryptionKey = первые keyLengthBytes байт # сейчас 16 байт для всех четырёх шифров
```

Знаковый нулевой байт `BigInteger.toByteArray()` удаляется, а представление
дополняется нулями слева до L байт. При одинаковых S и p участники получают одинаковые
байты независимо от того, сколько байтов требовалось для записи самого числа.
Секреты вне диапазона 2…p−2 и длины ключа вне 1…32 байт отклоняются.

После вычисления секрета проверенным протоколом MQV ключ передаётся выбранному шифру:

```java
Sha3Hasher hashFunction = new Sha3Hasher();
MqvKeyDerivation keyDerivation = new MqvKeyDerivation(subgroupParameters, hashFunction);
BigInteger sharedSecret = mqvProtocol.calculateSharedSecret(otherParticipantData);
StreamCipher cipher = algorithm.createCipher();
byte[] encryptionKey = keyDerivation.deriveKey(sharedSecret, cipher.getKeyLengthBytes());
cipher.initialize(encryptionKey, initializationVector);
```

Здесь `algorithm` — выбранное значение `StreamCipherAlgorithm`, а IV подготавливается
отдельно для нового сообщения. SHA3-256 использует стандартный `MessageDigest`,
выдаёт 32 байта и сбрасывает своё состояние после `digest`. Один объект хеширования
используется последовательно в одном потоке. Временные массивы секрета и полного
хеша в `deriveKey` перезаписываются нулями после копирования ключа.

### Замеры хеширования

В IDEA выберите **SecureTransfer - RGZ KeyDerivationBenchmarkMain**. Аргументы не нужны.
В `RgzSettings` используются:

| Настройка | Значение |
| --- | --- |
| `KEY_AGREEMENT_GROUP_SETTINGS` | p — 3072 бита, q — 256 бит |
| `KEY_DERIVATION_BENCHMARK_SETTINGS` | 1000 операций прогрева; 100 серий по 10 операций |
| `DERIVED_KEY_LENGTH_BYTES` | 16 байт |

Параметры подгруппы создаются в `data/rgz/params/subgroup.properties`, если файла нет.
Для p длиной 3072 бита вход хеша всегда составляет 384 байта. В одном запуске JVM
измеряются семь этапов:

1. Генерация временного секретного ключа MQV.
2. Вычисление временного открытого ключа MQV.
3. Вычисление общего секрета MQV.
4. Представление готового секрета в байтах фиксированной длины.
5. SHA3-256 уже подготовленных байтов, включая создание массива результата хеша.
6. Получение ключа из готового секрета: кодирование, хеширование, копирование нужных
   байтов и очистка временных массивов.
7. Вычисление общего секрета MQV и последующее получение ключа шифра.

Параметры, долговременные ключи, справочник, проверка подписи и входы для замеров
готовятся заранее. Экземпляр `MessageDigest` и поиск провайдера также находятся
вне замеров. Служебные циклы показываются отдельно и не вычитаются.
Сравниваются отношения медиан одного запуска; медианы отдельных этапов не складываются.

```text
data/rgz/reports/key-derivation/<дата-время-идентификатор>/
├── measurements.csv
└── report.html
```

HTML строится из CSV и содержит условия, семь этапов и стоимость хеширования
относительно трёх операций MQV. Секреты и ключи в отчёт не включаются.

Документация: [провайдеры Java 17](https://docs.oracle.com/en/java/javase/17/security/oracle-providers.html),
[MessageDigest](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/security/MessageDigest.html),
[BigInteger.toByteArray](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigInteger.html#toByteArray()).

## Передача файлов РГЗ — пункты 16–21

Для приложения выбран **Sosemanuk** по медиане генерации потока в проведённом
сравнении. Каждый файл передаётся в отдельном подтверждённом сеансе MQV.
Ключ шифрования получается через SHA3-256; отдельный ключ HMAC-SHA256 защищает
заголовок, IV, шифротекст и служебные подтверждения.

Запуск в IDEA:

1. **SecureTransfer - RGZ FileReceiverMain** — каталог и порт вводятся в консоли;
   по умолчанию `data/rgz/received` и `6060`. Дождитесь сообщения об ожидании подключения.
2. **SecureTransfer - RGZ FileSenderMain** — путь к файлу, адрес получателя и порт;
   для одного компьютера адрес `127.0.0.1`.

Получатель продолжает принимать следующие файлы. Рабочие буферы имеют размер
64 КиБ, полный файл в память не загружается. IV резервируется до передачи
в постоянном журнале `data/rgz/state/iv-sequence.log`.
Файл публикуется после проверки HMAC и точного конца запроса; существующие файлы
не заменяются. Незавершённые данные находятся в служебном `.part` и очищаются
при ошибке либо следующем запуске после остановки процесса.

Подробные инструкции для одного и двух компьютеров, формат полей,
правила сохранения журнала IV и разбор кода: [FILE_TRANSFER.md](FILE_TRANSFER.md).

## Сетевой обмен первой лабораторной

1. Запустите `KeyAgreementServerMain`.
2. В консоли сервера выберите алгоритм: 1 — DH полной группы, 2 — DH подгруппы, 3 — MQV.
3. Дождитесь сообщения «Сервер ожидает подключение на порту 5055».
4. Запустите `KeyAgreementClientMain`.
5. Сравните общий секрет в обеих консолях.

Клиент получает выбор алгоритма от сервера. Сервер обслуживает одно подключение
и завершает работу; для нового обмена запустите его снова.
В учебных примерах используются маленькие числа: p — 16 бит, q подгруппы — 8 бит.

По умолчанию клиент подключается к `127.0.0.1:5055`.
Для двух компьютеров в одной локальной сети укажите адрес сервера в общем меню
или в **Program arguments** конфигурации клиента: `192.168.1.10 5055`.
Серверу можно передать порт, например `5056`.
Брандмауэр компьютера с сервером должен разрешать входящее подключение на выбранный порт.

### Подготовка MQV

Сервер представляет Алису, клиент — Боба. При первом выборе MQV сервер подготавливает:

| Файл | Содержимое |
| --- | --- |
| `data/lab1/keys/alice-long-term.properties` | Секретная и открытая долговременная пара Алисы |
| `data/lab1/keys/bob-long-term.properties` | Секретная и открытая долговременная пара Боба |
| `data/lab1/trust/mqv-directory.properties` | Подписанный справочник открытых ключей |
| `data/lab1/trust/authority-public.der` | Доверенный открытый ключ центра для проверки подписи |

Долговременные пары и справочник используются повторно, временные пары создаются
для каждого обмена. Секретный ключ учебного центра применяется при подготовке подписи
и остаётся только в памяти. Неполный или несовместимый набор файлов вызывает ошибку.

На одном компьютере оба процесса читают общую папку `data/lab1/`.
Для запуска на двух компьютерах заранее передайте клиенту по доверенному каналу:

- `data/lab1/keys/bob-long-term.properties`;
- `data/lab1/trust/mqv-directory.properties`;
- `data/lab1/trust/authority-public.der`.

Сохраните относительные пути в рабочей папке клиента.
Параметры группы клиент получает от сервера и проверяет по справочнику.
По TCP передаются алгоритм, открытые параметры и открытые ключи.
Секретные ключи и общий секрет выводятся только локально в учебных примерах.

## Замеры — пункт 19

Запустите `BenchmarkMain` без аргументов или выберите пункт **6** общего меню.
Настройки собраны в именованных константах `lab1/config/Lab1Settings`:

| Настройка | Значение |
| --- | --- |
| Длина p | 1024 бита |
| Длина q подгруппы | 160 бит |
| Прогрев каждого этапа | 1000 операций |
| Число замеров этапа | 100 |
| Операций в одном замере | 10 |

Для q длиной 256 бит в `Lab1Settings.BENCHMARK_GROUP_SETTINGS` замените `160` на `256`.
Параметры замеров хранятся в `data/lab1/params/benchmark/` отдельно от маленьких учебных
параметров. Первая генерация большого простого p может занять время.

Для каждого алгоритма измеряются три этапа одного участника:

1. Генерация секретного ключа.
2. Вычисление открытого ключа.
3. Вычисление общего секрета.

DH в подгруппе и MQV используют одну подгруппу.
Для открытых и общих ключей заранее готовятся 64 различных набора входа,
используемых по кругу. Секретный ключ при измерении генерации каждый раз выбирается заново.
Долговременные ключи MQV, подпись справочника и её проверка подготавливаются заранее.
Вырожденные временные пары MQV отбрасываются при подготовке: измеряется успешное вычисление
секрета без стоимости повторного выбора ключей. Совпадение секретов проверяется до замеров.

Файлы, сеть, проверка параметров и консольный вывод находятся вне измеряемых интервалов.
Оба чтения счётчика и вычисление выполняются в одном потоке.
Каждый полученный результат используется после второго чтения счётчика.
Финальное хэширование в этой лабораторной пока не применяется.

Программа выводит медиану, среднее, минимум и максимум циклов на операцию.
Это статистика стоимости серий, делённой на число операций в серии.
Исходные циклы серий сохраняются в объектах `StageMeasurement`, затем записываются в CSV.
Пустая серия показывает служебные затраты отдельно, без автоматического вычитания.
Фиксированный прогрев не гарантирует установившуюся производительность JVM;
сборка мусора и фоновая нагрузка могут влиять на разброс.

### Отчёт — пункт 20

После успешного завершения всех девяти этапов `BenchmarkMain` автоматически создаёт:

```text
data/lab1/reports/<дата-время-идентификатор>/
├── measurements.csv
└── report.html
```

Пути к обоим файлам выводятся в консоли. Откройте `report.html` обычным браузером:
в нём есть сравнительная таблица, выводы по фактическим медианам, условия запуска
и отдельное описание служебных затрат. Кнопка «Печать / PDF» использует печать браузера.
Каждый запуск получает новую папку; предыдущие результаты сохраняются.

CSV содержит исходные целочисленные циклы серий. Столбцы:
`kind,algorithm,stage,measurement_index,operations,cycles`.
Тип `stage` обозначает этап алгоритма, `overhead` — пустую операцию.
При стандартных настройках сохраняется 1000 строк данных: 900 для этапов и 100 служебных.
Для перехода к циклам на операцию используется `cycles / operations`.

`BenchmarkReportWriter` сначала сохраняет CSV через `BenchmarkCsvFileStorage`,
затем перечитывает его и по восстановленным показаниям строит таблицу и выводы.
HTML содержит оформление и текстовую копию исходного CSV; интернет и веб-сервер
для просмотра не требуются. Ссылка на отдельный CSV работает, пока оба файла лежат рядом.
В отчёте сохраняются размеры p/q, настройки прогрева, ОС, архитектура JVM,
версия Java и описание счётчика. Секретные ключи в эти файлы не записываются.

HTML-шаблон находится в `src/main/resources/lab1/benchmark-report.html`.
Эта папка отмечена в модуле IDEA как ресурсы и копируется при сборке.
Редактировать оформление можно отдельно от Java-кода.

Выводы сопоставляют одинаковые этапы в одном запуске. Они не устанавливают
статистическую значимость и не описывают длительность полного сетевого сеанса.
Для коротких вычислений отдельно отмечается масштаб служебных затрат.

### Системные счётчики

Поддерживаются macOS, Windows и Linux на x86-64 и ARM64. JNA выбирает нативный адаптер
для архитектуры запущенной Java.

| Реализация | Системный API | Область учёта |
| --- | --- | --- |
| `MacOsCpuCycleCounter` | `thread_selfcounts` | Аппаратные циклы потока; macOS 12.4+ и поддержка оборудования |
| `WindowsCpuCycleCounter` | `QueryThreadCycleTime` | Циклы потока, включая режим ядра; трактовка тактов зависит от CPU |
| `LinuxCpuCycleCounter` | `perf_event_open` | Аппаратные циклы потока без ядра и гипервизора |

Доступность зависит от оборудования и разрешений ОС. Например, Linux может запрещать
perf обычному пользователю. При недоступности счётчика программа сообщает причину;
локальные алгоритмы и сетевой обмен запускаются независимо.
Сравнивать результаты следует на одной машине, в одной ОС и с одной реализацией счётчика.
