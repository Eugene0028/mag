# Передача файлов РГЗ — пункты 16–21

## Запуск в IDEA на одном компьютере

1. Запустите **SecureTransfer - RGZ FileReceiverMain**.
2. Укажите каталог приёма или нажмите Enter для `data/rgz/received`.
3. Укажите порт или нажмите Enter для **6060**.
4. Дождитесь сообщения «Получатель ожидает подключение». При первом запуске
   будут подготовлены параметры подгруппы, долговременные пары и подписанный справочник MQV.
5. Запустите **SecureTransfer - RGZ FileSenderMain** во втором процессе IDEA.
6. Введите путь к обычному файлу. Адрес `127.0.0.1` и порт `6060` можно принять нажатием Enter.
7. Успех отправки отображается после получения и проверки подтверждения сервера.

Получатель продолжает ждать следующие файлы. Каждый запуск отправителя открывает
новое соединение и выполняет новый обмен MQV. Один сеанс передаёт один файл.
Остановка получателя — Stop в IDEA или Ctrl+C. Параметры вводятся в консоли;
аргументы конфигураций запуска не требуются.

Если имя уже существует в каталоге приёма, файл отклоняется. Для повторной отправки
того же имени нужно выбрать другой каталог или заранее переименовать имеющийся файл.

## Два компьютера

Получатель играет роль **Alice**, отправитель — **Bob**. Получатель создаёт комплект
учебного доверия при первом запуске. Отправителю заранее передаются по доверенному
каналу следующие три файла с сохранением относительных путей:

```text
data/rgz/keys/bob-long-term.properties
data/rgz/trust/mqv-directory.properties
data/rgz/trust/authority-public.der
```

Долговременный секрет Alice остаётся у получателя. Открытые параметры подгруппы
отправитель получает по TCP и сверяет с доверенными материалами. В консоли
отправителя указывается IP компьютера-получателя и тот же порт. ОС получателя
должна разрешать входящее подключение на этот порт.

### Если справочник MQV не подходит

Клонирование репозитория переносит исходники; рабочие файлы `data/` исключены из Git.
Если получатель на втором компьютере создал собственную группу и справочник,
отправитель должен получить именно его клиентский комплект из трёх файлов выше.
Комплекты, независимо созданные на разных компьютерах, не согласованы между собой.

Файлы передаются от компьютера с `FileReceiverMain` к компьютеру с `FileSenderMain`
или удалённым режимом `TransferExperimentMain`. Направление определяется ролью,
поэтому получателем может быть Windows, а отправителем — Mac.
Перед заменой сохраните прежние три файла отправителя в отдельном каталоге.
Параметры группы отправитель получает по TCP; файл `params/subgroup.properties`
для клиентского обмена копировать не требуется.

Относительный путь `data/rgz` отсчитывается от **Working directory** конфигурации
запуска IDEA. Ориентируйтесь на абсолютные пути в логе: при рабочей папке `mag`
файлы будут в `mag/data/rgz`, при рабочей папке `securetransfer` —
в `securetransfer/data/rgz`. Если изменить рабочую папку получателя, он может
создать другой комплект в новом месте.

Сообщение «Справочник создан для других параметров подгруппы» означает, что
локальный справочник не соответствует группе получателя. Разрыв соединения
отправителем на этом шаге может отображаться у получателя как `EOFException`.

## 16. Выбранный шифр

В `RgzSettings.FILE_CIPHER` установлен **Sosemanuk**: в локальном сравнении
от 19.10.2026 его медиана генерации составила **2.3623 цикл/байт** против
4.6557 у HC-128, 7.8888 у Rabbit и 10.5966 у Salsa20/20. Для передачи файлов
учитывается стоимость обработки всего содержимого. Результат относится к этим
Java-реализациям и этому компьютеру.

Ключ Sosemanuk — 16 байт, IV — 16 байт. Приложение проверяет, что шифр в заголовке
совпадает с настроенным. Существующие точки сравнения по-прежнему доступны
для всех четырёх алгоритмов.

Исходные результаты: `data/rgz/reports/stream-ciphers/2026-10-19_11-23-40-a375d6f4/`.

## 17. Формат передачи

Все числовые поля собственного формата записываются старшим байтом вперёд.
Строки заголовка и ответа — UTF-8 с 32-битной длиной в байтах.

Порядок одного TCP-соединения:

1. Сервер передаёт magic `STFS` и версию `1` — два 32-битных числа.
2. Сервер и клиент обмениваются открытыми данными через общий `KeyExchangeTransport`.
3. Сервер и клиент по очереди передают 32-байтовые HMAC подтверждения ключей
   с разными метками ролей.
4. Клиент отправляет кадр заголовка файла, шифротекст и 32-байтовый HMAC файла.
5. Клиент завершает направление отправки TCP через `shutdownOutput`.
6. Сервер проверяет данные, сохраняет результат и возвращает защищённое подтверждение.

Кадр заголовка начинается с 32-битной длины, не превышающей 1024 байта.
Внутри находятся:

| Поле | Представление |
| --- | --- |
| Magic | `STFH`, 4 байта |
| Версия | `1`, 4 байта |
| Длина имени | 4 байта |
| Имя | До 255 байт UTF-8, без каталогов |
| Размер исходного файла | Неотрицательное 64-битное число |
| Идентификатор шифра | 4 байта: HC-128 — 1, Rabbit — 2, Salsa20 — 3, Sosemanuk — 4 |
| Длина IV | 4 байта; для Sosemanuk — 16 |
| IV | Указанное число байтов |

За заголовком следует ровно столько байтов шифротекста, сколько указано в размере
файла. Потоковый шифр не добавляет заполнение. Дальше идут 32 байта HMAC и конец
направления отправки. Лишние байты, неизвестная версия, неверный шифр, повреждённый
UTF-8 и недопустимые длины отклоняются. Имя проверяется на пути, управляющие символы
и распространённые ограничения имён Windows.

### Неповторяющиеся IV

`InitializationVectorSequence` хранит общий для ключей отправителя возрастающий
номер в `data/rgz/state/iv-sequence.log`. Перед использованием номер дописывается
в журнал под межпроцессной блокировкой; `FileChannel.force(true)` завершается
до выдачи IV. Номер кодируется в 16 байтах старшим байтом вперёд.

Неудачная передача расходует зарезервированный номер. При повторном запуске
последовательность продолжается. Незавершённая, повреждённая или несогласованная
запись приводит к отказу; автоматического сброса счётчика нет. Переполнение
не допускается.

Журнал является постоянным состоянием отправителя. При переносе установки
сохраняют его актуальную копию; удаление или откат журнала уничтожает историю
резервирований и гарантию неповторения. Файл не содержит секретных ключей.

## 18. Обработка файла частями

`FileCipher.encrypt` и `FileCipher.decrypt` выделяют два буфера по 64 КиБ.
Полный файл не загружается в память. Шифр инициализируется один раз по ключу и IV,
после чего `processBytes` продолжает одно состояние до конца файла.

Граница последней порции может быть любой. Адаптер Sosemanuk сохраняет остаток
80-байтового блока между вызовами. HMAC в обоих направлениях получает именно
шифротекст. Пустой файл имеет заголовок и HMAC без тела.

Если исходный файл оказался короче заявленного размера, отправка прерывается.
Увеличение файла обнаруживается дополнительным чтением после ожидаемого конца.
Содержимое файла передаётся в том виде, в котором оно было прочитано; снимок
файла при одновременной записи другими программами не создаётся.

## 19. Подготовка сеанса MQV

`FileTransferSession` использует общие `KeyAgreementProtocolFactory`,
`MqvProtocol` и `KeyExchangeTransport` с настройками РГЗ: p — 3072 бита,
q — 256 бит. Для каждого соединения создаются новые временные пары.
Собеседники проверяют подписанный справочник и открытые данные общей реализацией.

После вычисления секрета S формируются:

- **Ключ шифра:** первые 16 байт SHA3-256 от беззнакового представления S длиной 384 байта.
- **Хеш обмена T:** SHA3-256 двух канонически закодированных открытых сообщений
  `KeyExchangeTransport` в порядке «сервер, клиент».
- **Отдельный ключ HMAC:** SHA3-256 от UTF-8 метки `securetransfer/rgz/file-auth/v1`
  с завершающим нулевым байтом, байтов S и 32 байт T.

Подтверждение роли вычисляется HMAC-SHA256 с отдельной меткой и T. Неудачное
подтверждение закрывает соединение до отправки файла. Это связывает дальнейшие
данные и ответ с данным обменом MQV. Секреты и полученные ключи по сети не передаются
и в консоль не выводятся. При закрытии сеанса принадлежащие ему массивы ключей
перезаписываются нулями.

## 20. Сетевые стороны

`FileReceiverMain` последовательно принимает соединения. На каждый файл он создаёт
новый MQV-сеанс. Ошибка одного соединения выводится в консоль, затем сервер
подготавливает следующий сеанс.

`FileSenderMain` отправляет один выбранный файл. Порт приложения — 6060, отдельно
от первой лабораторной. Соединение имеет тайм-аут установки 5 секунд и тайм-аут
простоя отдельного чтения 30 секунд. Тайм-аут чтения не является общим временем
передачи или ограничением блокирующей записи TCP.

## 21. Целостность, завершение и ошибки

HMAC-SHA256 вычисляется с отдельным ключом и меткой назначения. Тег файла включает
контекст сеанса, точный кадр заголовка вместе с его длиной и весь шифротекст.
Теги сравниваются через `MessageDigest.isEqual`.

Расшифрованные байты первоначально записываются в служебный
`.securetransfer-incoming/receive-*.part` внутри выбранного каталога. Публикация
под исходным именем выполняется после проверки HMAC, точного размера и конца
запроса. Существующий файл не заменяется. Успешный ответ отправляется после
закрытия и публикации файла; ответ также имеет HMAC с отдельной меткой.

При обрыве, неверном теге, ошибке размера или диска временный файл удаляется.
Если удалить его не удалось, дополнительная ошибка выводится в консоль.
Служебные `.part`, оставшиеся после остановки процесса, удаляются при следующем
запуске получателя. Межпроцессная блокировка служебного каталога исключает
одновременную работу двух получателей с одним каталогом и очистку активного приёма.
Этот служебный каталог предназначен для файлов приложения.

Если соединение оборвалось после сохранения файла, но до получения ответа,
отправитель сообщает, что результат не подтверждён и файл мог быть сохранён.
Автоматического повторения передачи нет. Для каждой следующей попытки используется
новый сеанс MQV и новый зарезервированный IV.

## Откуда читать код

1. `FileReceiverMain` и `FileSenderMain` — порядок сетевых действий.
2. `network/FileTransferSession` — общий MQV, получение ключей и подтверждение.
3. `network/FileSender` и `network/FileReceiver` — жизненный цикл одного файла.
4. `network/FileTransferProtocol` — кадры и поля формата.
5. `file/FileCipher` — цикл обработки через буфер.
6. `file/InitializationVectorSequence` — постоянное резервирование IV.

Все эти классы находятся в `securetransfer.rgz`. Общая математическая часть
первой лабораторной используется через обычные импорты.
